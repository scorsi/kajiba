# kajiba — milestone plan

Technical milestones, no calendar. Each milestone has a verifiable **deliverable**, explicit **acceptance criteria**, the **tests** that prove them, and the **delegable** part (tests, boilerplate, refactoring). A milestone is closed when its criteria pass on `aarch64-linux` in `nix flake check` and, from J4, in the `e2e` job (0015); a milestone never leaves `nix flake check` red in between. Checks that need a real deployment are not product criteria: they belong to the deployment repository.

ADR references in parentheses. nixosTest names are flake attributes `checks.<linux system>.<name>`.

**Delivery order** (owner decision, 2026-10-30): J6 is delivered before J5. Milestone numbers stay as they are because ADRs reference them; the CI pages of the UI belong to J5.

## J0 — Skeleton: a green repository at the first commit (done)

**Deliverable**: the `kajiba` monorepo (0018) with a GitHub mirror, `nix flake check` green, no feature.

- `nix build .#kajiba-server .#kajiba-runner .#kajiba-cli .#kajiba-ui` produce artifacts; `kajiba-server --version` prints the workspace version.

## J3 — The server/git-side split, then writes over SSH, hooks, permissions, signatures

**Deliverable**: the forge runs as two units and two users (0052): `kajiba-server` never writes a repository, `kajiba-git` is the only writer and owns the SSH path; then `git push` over SSH, controlled by permissions and ref rules, with mandatory signatures.

Content: the split of 0052–0054 is built first, with J2's repository writes (reconciliation creation and `HEAD`, orphan quarantine, `admin import`) moved behind the git side's daemon and its sessions (0053) before any push is accepted. Then the SSH path: dedicated sshd instance in the module logging in as `kajiba-git`, `AuthorizedKeysCommand` → `kajiba-git ssh-keys`, `kajiba-git serve-ssh` handing its descriptors to the daemon, which spawns `git receive-pack`/`upload-pack` (0004, 0053); keys come from the configuration (0014), no key-mutating RPC; `kajiba-git hook pre-receive|post-receive` → `kajiba.hook.v1` on the daemon's socket, which runs the object-dependent checks in the quarantine and calls `kajiba.gate.v1.PreReceive` on the server, which keeps the policy, the admission gate and `pending_push` reconciliation (0003, 0026, 0052, 0053); global `core.hooksPath`; read/write/admin RBAC + `is_admin`, repository permissions from the configuration (0014, 0026); ref rules of 0013/0014, fixed by the product, per-pattern rules declared only (0026); signature algorithm of 0014 run by the daemon with `allowed_signers` from `OpenSession`; `push` events (0017); `/readyz` checks the git-side link and the sshd integration. `AuthorizedKeysCommand` prints the forced-command line of 0004 (`command="kajiba-git serve-ssh --user <public id>",restrict <key>`) whose key part is the canonical stored key (`ssh_key.public_key`, no comment), never the configured line. Tasks 1–2 close the two read-path bounds that only a repository writer can exercise (J2 review); tasks 3–6 were delivered in `kajiba-server` before the split decision and move to `kajiba-git` in task 16.

Ordered tasks; each is one feature, closable in one sitting with its tests, in one commit, and leaves `nix flake check` green. Tasks 1–6 are done and record the pre-split server identity. Tasks 7–16 build the split; no SSH write is accepted before tasks 17–23 are complete; the final two tasks split the acceptance coverage between `nixos-git-ssh` and `nixos-git-ssh-recovery`. No automatic migration of a J2 layout is needed: nothing is deployed; nixosTests start from the new layout (0052).

Tests: an oversized ancestor beyond the returned page and at a cursor boundary cannot induce an unbounded read through an accepted push; valid histories retain their ordering and pagination; header kind and size boundaries are checked before loading the affected objects.
2. **Complete `ListCommits` page budget** (0047): count author name, author email and parents as well as messages in the existing 1 MiB page budget, recording the amendment to 0047 in the new browsing-bounds ADR. Tests: large author fields and many parents shorten a page even with tiny messages; exact budget boundary, continuation without skipped or repeated commits, and a final empty page with no token.
3. **Repository role checks** (0013, 0014, 0026, 0028): one shared permission check over reconciled identity and repository permissions, including implicit owner `admin`, global `is_admin`, disabled users and the prohibition on external-user writes; no permission mutation API. Tests: the read/write/admin matrix, owner and global admin, disabled or external user, removed permission and archived repository.
4. **SSH auth-key lookup and `ssh-keys`** (0003, 0004, 0014, 0028): fingerprint lookup over the local socket resolves an active user's auth key; implement `kajiba-server ssh-keys <fingerprint>` under 0004's `AuthorizedKeysCommand` contract using the canonical stored `ssh_key.public_key`, without a comment or configured-line text. No key-mutating RPC. Tests: known auth key, unknown fingerprint, signing-only key, disabled user, removed or reassigned declared key, configured comments/options never echoed, and the output contract of 0004.
5. **SSH original-command parser** (0004, 0021): parse only `git-upload-pack` and `git-receive-pack` with a repository address, using the shared name/path validator and no shell evaluation. Tests: both Git commands, documented SSH URL path forms, optional `.git`, malformed quoting, extra arguments, traversal, shell metacharacters and every other command refused.
6. **Hook protocol and thin hook commands** (0003, 0014, 0020): define `kajiba.hook.v1` in `proto/`, regenerate the committed client, and add the service to the existing `/run/kajiba/local.sock` alongside the admin service (owner `kajiba`, 0600, as 0003 specifies). `kajiba-server hook pre-receive|post-receive` validates stdin and the transport context, then makes one local RPC; carry the quarantine context needed by server-side Git checks without moving policy into the hook. Admission stays refused until task 21 is wired. Tests: ordered update parsing including zero ids, malformed input/context, one call per invocation, missing socket gives an explicit failure, no hook service on the public listener, admin transport still works, and socket access remains restricted; proto lint and generated-code freshness checks.
7. **Rename the GitStore library** (0002, 0018, 0054): rename `kajiba-git` to `kajiba-gitstore` and `crates/kajiba-git/` to `crates/kajiba-gitstore/` before creating the new binary crate; update workspace members, dependency paths and package names, Rust imports, lockfile, tests, fixtures, Nix references, `versions-identical`, `CLAUDE.md` and `CONTRIBUTING.md` where they name the library. - `nixos-git-http`, `nixos-repo-lifecycle` and `nixos-git-ssh` still pass, their `RepoService` calls authenticated; smart HTTP and `/raw/` stay anonymous.
- `e2e` (WebAuthn virtual authenticator): enrollment through the `admin enroll` link, logout, login again, session invalidated after expiry; a second `admin enroll` revokes the passkey; wrong-origin ceremony refused.
- `buf breaking` runs (informational before 1.0); `proto-generated` stays clean.

**Delegable**: clap skeleton, interceptor tests, e2e scenarios.

2. **`GetWorktreeBase` and the creation checks** (0014, 0020, 0097): `RunService.GetWorktreeBase` returns the ids of `refs/heads/*` and `refs/tags/*`; one shared check for both methods, in 0097's order: `ci:trigger`, read then `write` role, archived, CI disabled, check and system names, no declared runner matching the requirements, 4 active worktree runs per user. **Acceptance criteria** (`nixos-ci`, nodes `forge` + `runner`, Nix closure preloaded)

- The runner connects with the declared secret, shows up with its declared capabilities; wrong secret → refused; a capability beyond the declaration → refused (`runner-refused`, reason `capabilities`); different `0.minor` → refused (0023); a runner host with `sandbox = false` refuses to start.
- Signed push on `main` of a repository with CI enabled → run created, executed, success; failing `flake check` → run failed with logs.
- Push on `refs/contrib/*` (injected in test by the forge) → no run; manual `TriggerRun` on that sha → run.
- `kajiba-server` restart during a job → the runner reconnects, the job finishes, the result is recorded exactly once; no log chunk lost or duplicated.
- Runner killed during a job → lease expired → attempt `lost`, then a new attempt on a compatible runner if replayable; a late result from the old attempt is ignored.
- Job requiring an absent backend → stays "pending" with a visible reason.
- CLI `ci watch` shows the stream and exits with the run's code.
- Runner journal passes `nisshi validate --logs`.
- Worktree (`nixos-ci-worktree`): from `client`, with uncommitted changes, `kajiba ci run --worktree` as a `write` user with a `ci:trigger` PAT → run on `runner`, logs streamed, exit 0; a change that breaks a check → exit non-zero with logs; no new ref, branch or stash on the forge or the clone, and the captured commit is not fetchable over git transport.
- Worktree: `--check a` builds only `checks.<system>.a`; a check with `requiredSystemFeatures = [ "kvm" ]` runs only on a runner tagged `kvm`.
- Worktree: `read` user → `ROLE_MISSING`; PAT without `ci:trigger` → `SCOPE_MISSING`; bundle above 64 MiB → `BUNDLE_TOO_LARGE`; no declared runner for the system → `NO_MATCHING_RUNNER`; the run and its bundle are gone after `ci.worktree_retention`.

**Delegable**: test machinery (minimal flake with a trivial check, store preloading), lease/reconnection tests, proto message boilerplate.

## J7 — Mirroring to GitHub

**Deliverable**: declared mirrors are pushed to GitHub, queued, with unlimited retries and reconciliation; GitHub targets are created and kept configured (0027).

Content: mirrors from the configuration (0026), read-only `MirrorService` (status), `mirror` bus handler, coalesced queue in the DB, capped backoff, reconciliation timer, explicit refspecs with scoped `--prune` (0011); GitHub target preparation (create if missing, description, homepage, visibility, archived, issues/wiki/projects/discussions/pull requests/Actions disabled; never delete or rename), `github` mirror fields, `mirror.prepared_digest`, `mirror-prepared` (0027); the token permissions marked "to verify in J7" in 0027 checked first; per-mirror status in the UI and `kajiba mirror status`.

**Acceptance criteria** (`nixos-mirror`, node `remote` = bare repo behind sshd or HTTP basic, simulating GitHub)

- Push → `remote` up to date within N seconds; branch and tag deletion and force-push propagated; tags propagated.
- `refs/contrib/*` never present on `remote`; a ref outside `refs/heads`/`refs/tags` created on `remote` is left untouched.
- `remote` unreachable → attempts with backoff, "failed" status visible; `remote` back → convergence without intervention; five pushes during the outage → a single mirror job at recovery.
- Reconciliation timer: ref modified by hand on `remote` → corrected on the next pass.
- Mirror enabled on a `remote` already identical → no ref updated.
- Credential absent or unreadable → explicit error in the status, no crash.
- GitHub target preparation against a fake GitHub API on `remote`: missing repository created, then pushed; drifted description, visibility or archived corrected on the next reconciliation pass; Actions and pull requests disabled; no delete or rename call ever sent; preparation failure → mirror error, no push; archived target prepared, never pushed.

**Delegable**: test `remote` node, outage simulation, coalescing tests.

## J8 — Operations: backup, timers, complete module

**Deliverable**: the forge is operable day to day: dump/restore tested, automatic cleanups, complete and documented NixOS module.

Content: `kajiba-server dump` under the write barrier across both units (0016, 0053: the server refuses new writing sessions and `PreReceive`, drains open sessions through `SessionExited` and their reconciliation, then snapshots the database and copies the repositories from its read access; the git side holds no barrier state), `restore` into two empty state directories (0052), `dump.keep` (0016); gc as `kajiba-git gc` maintenance sessions admitted through the gate (0052, 0053), retention, reconciliation and dump timers (0022); configuration reload on `SIGHUP` without restart for both daemons (new ADR to write: reload semantics and the settings that still require a restart, such as listen addresses, state directories, sockets and metrics listen); module options frozen for J9; operations documentation in the README.

**Acceptance criteria** (`nixos-ops`)

- Dump → new empty VM → restore → identical `git clone`, users, passkeys and runtime PATs working, historical runs visible; the restored `repos/` belongs to `kajiba-git` and the database to `kajiba-server`.
- Dump closes admission while an admitted push (a live `receive-pack` session of the git side) and another mutating operation are in flight → both drain, pending push events commit before the snapshot, restored refs and DB agree. New push, import or maintenance session during the barrier → refused with the maintenance message, accepted after; clones over HTTP and SSH keep working.
- Retention timer: logs older than the retention deleted, DB index consistent; `dump.keep` honored.
- Weekly `git gc` executed as `kajiba-git` without breaking a concurrent push; a gc session is refused while a dump holds the barrier and runs after it.
- Configuration-only change (a repository or user added) → `nixos-rebuild switch` reloads the service instead of restarting it (`Type=notify-reload`, `reloadIfChanged`): the new repository is clonable, a clone in progress completes, the process id is unchanged. Invalid configuration on reload → refused with a log line, previous configuration kept, service still ready. A change to a restart-only setting → reload refused with a message naming the setting.

**Delegable**: scripted restore procedure, timer tests.

# ADR 0007 — CLI: Rust, client from `kajiba-proto`

Status: Accepted — 2026-10-24 (replaces the Go CLI decided on 2026-10-09)

## Context

Initial uses: create a repo, trigger and follow a CI run. Targets: macOS and Linux, aarch64 first, x86_64 next. Windows: unplanned nice-to-have. The API is gRPC (0005). The first decision chose Go (grpc-go, cobra); the J0 skeleton has an empty Go module. A Go CLI costs a second toolchain in the flake (`buildGoModule`, `vendorHash`, Go in the devShell, `gofmt`), a second committed generated client, and a second implementation of anything the CLI shares with the server. kekkai made the same move for the same reasons (kekkai ADR 0033); here the Go side is still empty, so the move is cheapest now.

## Decision

- `kajiba-cli` is a **Rust** crate of the workspace in `apps/cli/`, binary **`kajiba`**: clap for commands, tonic client generated by `kajiba-proto` (which builds server and client code), text output and `--json` (protojson field names, enums as names).
- Distributed through Nix (`packages.kajiba-cli`, crane, like the server). Cross-compilation for other OSes later through the Rust toolchain.
- Authentication: personal access token (PAT, 0014) read from a file (`$XDG_CONFIG_HOME/kajiba/token`, mode 0600, or `--token-file`); `kajiba login` writes it. Device flow against the forge later.
- The CLI sends its version on every call; the server applies 0023's compatibility rule.
- Errors: `kajiba: <message>` on stderr, exit code 1; the gRPC reason (0020) is part of the message.

## Consequences

- One language for server, runner and CLI (0002); one generated contract, at build time (0020); `versions-identical` covers Cargo and `package.json` only (0023).
- No business logic in the CLI: it is a client.
- Removing the Go skeleton is a J1 task (milestones).

## Rejected alternatives

- Go (the 2026-10-09 decision): a second toolchain and generated client for no feature Rust lacks.
- Nim, Zig: no mature gRPC client.

# ADR 0002 — Language: Rust for the server, the runner and the CLI

Status: Accepted — 2026-10-09 (revised 2026-10-24: the CLI is Rust too, 0007)

## Context

Candidates: Rust, Go, Zig, multi-language. Constraints: a small single host where memory matters; showcase project; fear of compile times; Zig has no git/SSH/gRPC ecosystem.

## Decision

- Server, runner and CLI in **Rust** (stable toolchain).
- Cargo workspace (0018): `kajiba-core` (domain, permissions, events), `kajiba-git` (GitStore boundary), `kajiba-proto` (generated types, server and client), `kajiba-exec` (execution backends), `kajiba-server`, `kajiba-runner`, `kajiba-cli`.
- Binaries: **`kajiba-server`** (the daemon and its host-local subcommands: `serve`, `config check`, `ssh-keys`, `serve-ssh`, `hook`, `dump`, `restore`, `admin`) and **`kajiba`** (the CLI, 0007). Host-local subcommands never open the database themselves: they talk to the running server over its local socket (0003), so the server stays the single SQLite writer (0012); `config check` and `restore` are the only offline ones.
- Stacks: tokio, axum + tonic (+ tonic-web), sqlx (SQLite), gix (0003), webauthn-rs, tracing, clap.
- Compile comfort: `cargo check` in the loop, mold/lld linker in the devShell, crane on the Nix side (dependencies in a separate derivation), dev profiles without LTO.

## Consequences

- A single language for everything kajiba ships except the frontend (TypeScript, 0006).
- Low memory footprint, no external runtime on the host.
- Longer compile times than Go; mitigated by the crate split.

## Rejected alternatives

- Go: excellent for a server that spawns many processes, fast builds; brings nothing Rust doesn't offer here, and the memory footprint is less favorable.
- Zig: no mature git, SSH or gRPC library; reserved for a possible low-level execution backend later.
- A single binary for daemon and CLI: the CLI is installed on workstations, the daemon's subcommands only make sense on the forge host.

# ADR 0052 — Process and privilege split: server and git side

Status: Accepted — 2026-10-25

## Context

Until J2 one process, `kajiba-server` as user `kajiba`, owns everything: the database, the public HTTP/gRPC surface, authentication, CI, mirrors, and the bare repositories under `repos/`, which it creates, imports into and, from J3, lets `git receive-pack` write through the SSH path (0003, 0004). A vulnerability anywhere in that process (the web and gRPC stack, the runner protocol, git's network client during an import, git's `receive-pack` or the hooks) gives the whole forge: the database with its credential hashes, passkeys and sessions, every repository's history, and the mirror credentials.

The owner decides to split the server into two binaries, two systemd units and two system users, so that the public surface cannot write repository history and the git path cannot read the database. This ADR fixes who runs what, who owns which files, how the units start and what each one does when the other is down. ADR 0053 fixes the protocol between them, ADR 0054 the accepted names and the packaging. Each item below names the accepted ADR point it amends; everything else in those ADRs stands.

## Decision

### Two processes

- **`kajiba-server`**, user and group `kajiba-server`: the database (single SQLite writer, 0012), configuration reconciliation (0014, 0026), the HTTP/gRPC listener with the API, the UI, authentication, CI and the runner protocol, mirrors (including the mirror `git push`, which only reads the local repository), events and handlers (0017), the admin socket (`/run/kajiba/local.sock`, root and `kajiba-server` only, amends 0003), the admission gate and `pending_push` (0003), dumps (0016). It **reads repositories only**: gix browsing, `/raw/`, and smart HTTP `git upload-pack --stateless-rpc`. Smart HTTP stays here because `upload-pack` never writes, the HTTP listener is already this process's surface, and routing clones through the writer would put a public network listener on the side the split protects. The server never calls a `GitStore` write method and the filesystem refuses it if it did (below).
- **`kajiba-git`**, user and group `kajiba-git`: the **only writer of `repos/`**. Its daemon (`kajiba-git serve`) is the parent of every process that writes a repository: `git receive-pack` and `git upload-pack` for SSH sessions, the `git ls-remote` and `git fetch --atomic` of an `admin import` (0026, 0041), repository creation (`git init --bare` in its `tmp/`, `rename` into `repos/`, 0012), `HEAD` changes, orphan quarantine moves (0032) and, from J8, `git gc`. The dedicated sshd (0004) logs users in as `kajiba-git`; its `AuthorizedKeysCommand` and forced command are `kajiba-git ssh-keys` and `kajiba-git serve-ssh`; the hooks are `kajiba-git hook pre-receive|post-receive`. The git side has no database access, no public listener and no access to the server's state directory.
- **Object-dependent checks run on the git side.** `receive-pack` keeps pushed objects in a quarantine directory it creates with mode 0700, which the server cannot read. Computing the pushed commits (`git rev-list <new tips> --not <all refs>`), the fast-forward test and the SSH signature verification of commits and annotated tags (0014) therefore run in the daemon, with the pusher's `allowed_signers` and role handed to it by the server when the session opens (0053). The server keeps every check that needs no object: identity, roles, ref prefixes (0013), default-branch protection, who may force-push or delete, the per-repository gate and the `pending_push` commit. `pre-receive` remains the single control point of 0014: one hook call, whose evaluation spans the two processes.

### Users, directories, ownership

- Users: `kajiba-server` and `kajiba-git`, both fixed system users with a group of the same name, no `DynamicUser` (0022; naming amends 0015 in 0054). **`kajiba-server` is a member of group `kajiba-git`** and that is the only cross membership: it gives the server read access to repositories and to the daemon's runtime directory. `kajiba-git` is in no other group. The runner keeps user and group `kajiba-runner` (0054).
- **Amends 0012 — two state directories.** The server's `stateDir` (default `/var/lib/kajiba-server`, `kajiba-server:kajiba-server` 0750) holds `db/`, socket-related state, `ci/logs/`, `ci/artifacts/`, `tmp/`, server-side orphans in `tmp/orphans/` and `kajiba.lock`. The git side's `stateDir` (default `/var/lib/kajiba-git`, `kajiba-git:kajiba-git` 0750) holds `repos/<public id>.git`, `tmp/` (creation staging), `tmp/orphans/` (repository quarantine, 0032) and `kajiba-git.lock`, its own single-instance lock. Each is the `StateDirectory` of its own unit; the module exposes both paths (0054). Nothing under the server's directory is reachable by `kajiba-git`. Git-side staging and repository quarantine stay on the same filesystem as `repos/` because moves are renames. Both state directories and `dump.dir` are the persisted paths of an ephemeral root (0012).
- **Repository read permissions.** `/var/lib/kajiba-git` and every repository are group-readable and never group-writable: directories 0750, files 0640 (Git's immutable objects and packs may be 0440). `kajiba-git` enforces this with `core.sharedRepository=0640`, an explicit group-read mode set in every repository it creates, plus process umask 0027 for its own files and children. Umask alone is insufficient for Git's object and pack modes. The receive-pack quarantine remains private (0700) until objects are promoted; the server never reads it.
- **Read-only access and ownership trust.** The server opens repositories read-only with gix and runs read-only `upload-pack` children. Since `kajiba-git` owns them, the server explicitly trusts only repository paths under the configured git-side `stateDir`'s `repos/`: `safe.directory` for its Git children and gix ownership trust for its own reads. No wildcard trust of unrelated paths or owners. The server never writes there, also enforced by `ReadOnlyPaths=` in its unit.
- No deployment holds repositories yet (production readiness is J9). A J2 state directory is not migrated automatically: the operator moves `repos/` and `tmp/orphans/` once, with their ownership changed; nixosTests start from the new layout.
- Runtime directories: `/run/kajiba` (server, `kajiba-server:kajiba-server`, mode 0751 so that `kajiba-git` can reach the sockets inside) holds `local.sock` (admin: `kajiba-server` 0600, peers root and `kajiba-server`) and `git.sock` (for the git side: `kajiba-server:kajiba-git` 0660, peer `kajiba-git` only). `/run/kajiba-git` (`kajiba-git:kajiba-git`, 0750, traversable by `kajiba-server` through its group) holds `local.sock` (gRPC, peers `kajiba-server` and `kajiba-git`) and `ssh.sock` (raw session hand-off from `serve-ssh`, peer `kajiba-git` only). Every socket checks the peer uid before serving a request (0003); the file modes are defence in depth. Peer checks cannot tell the daemon from the sshd-spawned helpers, which share its uid: "helpers talk to the daemon" (0053) is a code organisation, not a boundary.
- Secrets: mirror credential files stay readable by `kajiba-server` only (the server pushes mirrors). Import credentials (0044) reach the git side over the socket for the duration of one import and are never written to its disk. Runner tokens, PAT hashes and the database never leave the server.

### systemd units

- `kajiba-server.service` keeps its hardening (0022) and gains: `User=`/`Group=kajiba-server`, `StateDirectory=kajiba-server` (0750, default `/var/lib/kajiba-server`), `ReadWritePaths=` its own `stateDir` and `dump.dir`, `ReadOnlyPaths=` the git side's `stateDir`, `SupplementaryGroups=kajiba-git`, `RuntimeDirectoryMode=0751`, `Wants=` and `After=kajiba-git.service`. It still needs `git` on its `PATH` for `upload-pack` and mirror pushes, and `AF_INET`/`AF_INET6` for its listeners. Configured state paths follow the module options (0054).
- `kajiba-git.service`: `User=`/`Group=kajiba-git`, `StateDirectory=kajiba-git` (0750, default `/var/lib/kajiba-git`), `RuntimeDirectory=kajiba-git` (0750), `UMask=0027`, `Type=notify` (`READY=1` once its sockets listen, written by the daemon itself over `$NOTIFY_SOCKET`; readiness does not probe HTTP), `KillMode=control-group` (the default: a stop kills every child, which 0053's recovery relies on), `Restart=on-failure`, `git` on its `PATH`, and the same hardening set as the server with these differences: `SocketBindDeny=any` with an allowance only for the configured metrics port when enabled (loopback-only, default disabled, 0054), `AF_INET`/`AF_INET6` kept for metrics and `git fetch` over the network during imports, and `InaccessiblePaths=` the server's `stateDir`, stating in the unit what the permissions already enforce. No `PrivateUsers` on either unit (peer uid checks). `LimitCORE=0`.
- The dedicated sshd unit (0004) runs after `kajiba-git.service` (`Wants=`, `After=`) and its helpers run under sshd's sandbox, not the daemon's: they inherit uid `kajiba-git` and nothing else from the split. The `kajiba-gc.timer` of J8 runs `kajiba-git gc`, which asks the daemon for maintenance sessions admitted by the server's gate (0053); it runs as `kajiba-git`, never as `kajiba-server`.
- Both units carry `restartTriggers` on their configuration file and their package: a `nixos-rebuild switch` restarts both in one transaction, and the version handshake of 0053 covers the window between the two restarts.

### Startup, readiness, one side down

- Boot order: `kajiba-git` first (it needs nothing from the server to become ready), then `kajiba-server`, whose startup reconciliation may need `CreateRepository`, `SetHead` or `QuarantineRepository` (0053). A reconciliation that needs the git side and cannot reach it fails startup with `fatal{err}` and the unit restarts (`Restart=on-failure`); a startup that needs no repository write does not need the git side at all. After declared-state reconciliation the server connects to the daemon, exchanges `Hello` and rebuilds its gate from `ListSessions` (0053) before pending-push recovery and before serving.
- **Amends 0022 — `/readyz`.** The server's `/readyz` includes the git-side link (connected, version accepted) as a subsystem, next to the local socket and, from J3, the sshd integration. The module's `ExecStartPost` therefore waits for both units to be up. The daemon's optional HTTP endpoint is `/metrics` only (0054); its readiness is `Type=notify`.
- **Git side down, server up**: browsing, `/raw/`, smart HTTP clone, the API, CI, mirrors and dumps of the database keep working. `admin import`, startup repository creation and SSH sessions fail with an explicit `UNAVAILABLE` (`MAINTENANCE` is not used: the reason is `GIT_SIDE_UNAVAILABLE`, 0020 table amended by 0053); sshd refuses logins because `ssh-keys` cannot resolve keys. `/readyz` fails. Pending rows whose session belonged to the dead daemon generation are reconciled when the daemon comes back (0053).
- **Server down, git side up**: the daemon accepts no new session (every session is opened by the server, 0053) and `serve-ssh` ends with an explicit message, the same clean refusal 0003 promised for a push during a restart. Sessions already running finish; the daemon keeps their exit facts for the server's return.
- **Both down**: nothing runs; the recovery matrix of 0053 applies at the next start.

### What the split gives, and what it does not

- A compromise of the server (its public HTTP/gRPC surface, the web authentication, the runner protocol, a handler) cannot write any repository's history: the only writes it can request are creating an empty repository, pointing `HEAD` at an existing branch, importing into a repository that still has **no ref** (the daemon checks this itself before fetching) and quarantining a directory. A compromise of the git side (git's `receive-pack`, `fetch` against a malicious import source, the hooks, the signature verification) cannot read the database, the CI artifacts, the mirror credentials or the runner tokens, cannot speak to the runners, and cannot call the admin socket. The large third-party attack surfaces are on opposite sides: the HTTP stack and SQLite on one, git's wire protocol code on the other.
- The git side can still write any repository: that is its job. A compromised daemon can skip the signature and fast-forward checks it performs and can write refs out of band; the server re-checks everything that needs no object at `PreReceive`, and an out-of-band write is outside the durability guarantee of 0003, as before. The daemon validates each request against the state it owns (public id syntax, directory present or absent, no ref before an import, refs under `refs/heads/` and `refs/tags/` only) instead of trusting the server.
- Both binaries sit world-readable in the Nix store, the configuration files are world-readable, and both units run on the same kernel under the same systemd: the gain is privilege and attack-surface separation, not secrecy of code or isolation from the host. Root, and anyone who can change the deployment, still holds everything.
- The hooks and `serve-ssh` run under sshd with uid `kajiba-git`: they can reach the daemon's sockets and the server's `git.sock` directly. Nothing stops a helper from calling the server itself; the split does not separate the helpers from the daemon.

### Amended points

- **0002**: a second host binary, `kajiba-git`, with the subcommands `serve`, `config check`, `ssh-keys`, `serve-ssh`, `hook`, `gc`; `kajiba-server` loses `ssh-keys`, `serve-ssh` and `hook`. J3 tasks 4–6 delivered `kajiba-server ssh-keys`, the SSH command parser and `kajiba-server hook pre-receive|post-receive` with `kajiba.hook.v1` on the admin socket before this decision; they move to `kajiba-git` unchanged in behaviour (`--user` stays the user's public id; the forced command names `kajiba-git`), and `kajiba.hook.v1` is served by the daemon (0053). Neither daemon's host-local subcommand opens the database.
- **0003**: the hook is `kajiba-git hook …` and its one gRPC call goes to the daemon's socket; the admission gate and `pending_push` stay in the server, fed by the daemon's session events (0053); the local socket paragraph is replaced by the socket inventory above.
- **0004**: the dedicated sshd runs as `kajiba-git`; `AuthorizedKeysCommandUser kajiba-git`, `kajiba-git ssh-keys`, forced command `kajiba-git serve-ssh --user <id>`.
- **0012**: layout split as above; "a single writer (the server process)" is unchanged for SQLite and now also names the git side as the single writer of `repos/`.
- **0015**: `nixosModules.server` declares both units (0054).
- **0016**: the dump copies repositories from the server's read access while the barrier holds; the barrier covers the git side's sessions (0053).
- **0022**: `/readyz` as above; every line `kajiba-git` writes on stderr follows the same log schema, and every nixosTest that starts it validates its journal too; the unit hardening list applies to both units with the differences above.
- **0026**: creation, `HEAD` changes and import are requested by the server and performed by the git side.
- **0032**: repository orphans live in the git side's `tmp/orphans/`; server-side orphans stay in the server's state directory. The server computes the orphan repository set (it reads `repos/` and the `repo` table) and asks the git side to move each orphan.

## Consequences

- A `nixos-rebuild switch` restarts two units; the operator sees two journals (`kajiba-server`, `kajiba-git`) and two state directories to persist.
- Every repository write becomes a local RPC and a child process of the daemon: one more hop per push admission, negligible at this scale.
- J3 builds the split before the SSH and hook features (milestones.md); J2's reconciliation and import move their writes behind the git side with tests before any push is accepted.
- The `GitStore` trait stays one trait: the server links the write methods but never calls them, and the filesystem refuses them. Splitting the trait is not needed for the guarantee.

## Rejected alternatives

- Keeping one process and dropping privileges per operation: Linux has no per-thread uid switch a Rust async server can use safely, and the public listener would still live in the process that writes repositories.
- Letting `serve-ssh` be the parent of `receive-pack` and reporting its exit over a connection: a connection drop is not proof the child has exited (0003 forbids inferring completion), so the daemon spawns the children itself and `waitpid` is the proof.
- Letting the hooks talk to the server directly: the server cannot read the quarantine, so signature and fast-forward checks would have no place to run.
- Routing smart HTTP through the git side: a public network listener on the writer side.
- One state directory with a shared parent and nested ownership: every file under it would need its own mode discipline (the lock file alone, if group-readable, lets the other user hold it); two `StateDirectory=` trees are what systemd does well.

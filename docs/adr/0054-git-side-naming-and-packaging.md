# ADR 0054 — Git side: crate, binary and package naming, Nix packaging

Status: Accepted — 2026-10-25

## Context

ADR 0052 adds a second host binary. ADR 0002 and 0018 fix the crate names (`kajiba-core`, `kajiba-git`, `kajiba-proto`, `kajiba-exec`, `kajiba-server`, `kajiba-runner`, `kajiba-cli`) and the layout (`crates/` for libraries, `apps/` for deliverables); ADR 0015 fixes the flake outputs and the module. Today `kajiba-git` is the library crate holding the `GitStore` boundary, used by the server and, after the split, by the git side as well. The new binary needs a name that also serves as unit, user, group, directory and option name, and a place in the workspace and the flake. Each item below names the accepted ADR point it amends; everything else in those ADRs stands.

## Decision

### Names

- **One name for every face of the git side**: binary `kajiba-git`, Cargo package `kajiba-git` in `apps/git/`, Nix package `packages.kajiba-git`, unit `kajiba-git.service`, system user and group `kajiba-git`, `StateDirectory=` and `RuntimeDirectory=` `kajiba-git` (`/var/lib/kajiba-git`, `/run/kajiba-git`), module options `services.kajiba-git`.
- **Library crate.** The existing `kajiba-git` library becomes `kajiba-gitstore` in `crates/kajiba-gitstore/` (it is the `GitStore` boundary and nothing else): Cargo forbids two packages with one name in a workspace, and the operator-facing name wins over the developer-facing one. The rename is an early J3 task, before creating the binary crate. ADR 0046's title keeps the historical name.
- **Amends 0015 — system identities follow binaries.** The server's user and group change from `kajiba` to `kajiba-server`; the git side uses `kajiba-git`; the runner keeps `kajiba-runner`. Socket ownership, peer checks, secret-file permissions and unit identities follow these names (0052, 0053).
- **Amends 0021 — SSH URLs.** The SSH login name is the git side's system user, so clone URLs become `ssh://kajiba-git@<host>:<port>/<owner>/<name>.git` and `kajiba-git@<host>:<owner>/<name>.git`. Nothing is deployed over SSH yet, so no URL changes for a user.
- **Amends 0002 and 0018.** Workspace: `crates/kajiba-git/` is renamed `crates/kajiba-gitstore/`; `apps/` gains `git/` next to `server/`, `runner/`, `cli/`, `ui/`. Shared code the two daemons need (configuration parsing, the log layer, the local-socket transport with its peer check, name and ref validation) lives in `kajiba-core` and `kajiba-gitstore`; the two app crates hold only their own commands. No new top-level library crate.

### Configuration (amends 0019)

- One TOML file per daemon, generated by the module, checked at build time by that binary's `config check`, unknown fields refused.
- Server file, fields added:

  | Field           | Default                      | Meaning                                            |
  | --------------- | ---------------------------- | -------------------------------------------------- |
  | `state_dir`     | `/var/lib/kajiba-server`     | server-owned state (0052); replaces 0012's default |
  | `git.state_dir` | `/var/lib/kajiba-git`        | where `repos/` is read from (0052)                 |
  | `git.socket`    | `/run/kajiba-git/local.sock` | the daemon's gRPC socket (0053)                    |

  `ssh.host` and `ssh.port` keep their display role (0019); `ssh.port` defaults to the git side's sshd port when both modules are evaluated on one host.

- Git side file:

  | Field            | Default                | Meaning                                                                 |
  | ---------------- | ---------------------- | ----------------------------------------------------------------------- |
  | `state_dir`      | `/var/lib/kajiba-git`  | `repos/`, `tmp/`, `tmp/orphans/`, `kajiba-git.lock` (0052)              |
  | `server_socket`  | `/run/kajiba/git.sock` | the server's `kajiba.gate.v1` socket (0053)                             |
  | `hooks_path`     | required               | the Nix store directory of the hook links (0003), written by the module |
  | `log.level`      | `info`                 | 0022                                                                    |
  | `metrics.listen` | `null`                 | optional loopback-only `/metrics` listener (0022)                       |

#### Metrics (amends 0022)

- `kajiba-git` serves `GET /metrics` on its optional `metrics.listen`, default `null` (disabled), following the server's masu convention: loopback only, refused otherwise by `config check` and asserted by the module; Prometheus text 0.0.4; closed labels, at most 500 series, no repository, user or path labels. It logs `metrics-listening{addr}` when enabled.
- Metric set:

  | Metric                                           | Labels                                                              |
  | ------------------------------------------------ | ------------------------------------------------------------------- |
  | `kajiba_git_build_info` (gauge 1)                | `version`                                                           |
  | `kajiba_git_sessions_active` (gauge)             | `kind` (`receive_pack`, `upload_pack`, `import`, `maintenance`)     |
  | `kajiba_git_sessions_total` (completed sessions) | `kind` (same set), `result` (`ok`, `error`, from child exit status) |

- Every nixosTest that enables this listener runs `masu validate --metrics` on it and checks a session counter moved; unit tests pin the exposition and label sets. Push admission counters stay on the server.

### Nix (amends 0015)

- `packages.kajiba-git`: a crane build like `kajiba-server`'s, `cargoExtraArgs = "--locked -p kajiba-git"`, same shared `cargoArtifacts`, `git` in `nativeCheckInputs` where tests spawn it, `meta.mainProgram = "kajiba-git"`. The hook directory (`pre-receive`, `post-receive` wrappers calling `kajiba-git hook …`) is a small derivation next to it, passed to the module as `hooks_path`; no per-repository hook file (0003).
- `nixosModules.server` declares **both** option trees and both units: a forge is never deployed with one side only. `services.kajiba-git` has no `enable`: it follows `services.kajiba-server.enable`. Options, mirroring the file one to one (0019, 0029): `package` (default `pkgs.kajiba-git`), `stateDir` (default `/var/lib/kajiba-git`), `log.level`, `metrics.listen` (default `null`), `ssh.port` (the dedicated sshd's port, default 2222, 0004). `services.kajiba-server.stateDir` defaults to `/var/lib/kajiba-server`; it and `services.kajiba-git.stateDir` configure each unit's own `StateDirectory` (amends 0012's single `stateDir`). `services.kajiba-server` gains `git.stateDir` and `git.socket`, defaulting from `services.kajiba-git`. `services.kajiba-server.persistedPaths` lists both state directories and `dump.dir`.
- Checks: `module-eval` evaluates both trees and asserts the generated units (users, groups, the `kajiba-server` membership in `kajiba-git`, both default and custom state paths, directory modes, `ReadOnlyPaths`, `Type=notify`, ordering, `hooks_path`, the sshd user and `AuthorizedKeysCommand`, metrics disabled by default and the bind allowance when enabled); `versions-identical` and the package builds cover the new crate as the others; `kajiba-git --version` prints `VERSION` (0023).
- `nixosModules.runner` and `darwinModules.runner` are untouched.

## Consequences

- Operators see one name on every surface of the git side: `journalctl -u kajiba-git`, `/var/lib/kajiba-git`, `services.kajiba-git`, the SSH login name.
- `CLAUDE.md`, `CONTRIBUTING.md` and the module descriptions are updated with `kajiba-gitstore` during the library rename and with `kajiba-git` during the task that creates the app crate.

## Rejected alternatives

- Alternative names were considered; `kajiba-git` is the accepted name.
- A second `[[bin]]` in the library crate: `crates/` holds libraries only (0018), and the binary's dependencies (tokio, tonic, clap) would be pulled into every user of the library.
- A `[[bin]]` in `kajiba-server`: the point of the split is two independent dependency sets and two packages; one crate would ship the SQLite stack into the writer's binary.
- A separate flake module for the git side: consumers import `nixosModules.server` and get a working forge; a second module would be a mandatory pair.
- Options nested under `services.kajiba-server.git.*` for the daemon itself: the daemon has its own file, unit and user; its options mirror its file (0019).
